# 需求文档

文档记录已经确认的产品行为。按功能点分节，每个场景用表格给出处理。实现步骤、表结构和接口示例不写在这里。

## 1. 确定输出路径

用户给出路径则用该路径。未给出则提问，得到路径再写。

要我们起文件名时，用 `需求-<功能名>.md`。功能名可以再带连字符。

已有 frontmatter 时保持原样，只补正文。

完成：目标路径已确定；已有 frontmatter 的键和值未改。

## 2. 采集事实

只收用户已经确认的规则。权限位、错误码、状态名、接口路径要和源码对上；对不上的不写入。用户没拍板的分支标成「未确认」，并且不写进正文。

| 事实                       | 来源                                   |
| -------------------------- | -------------------------------------- |
| 谁能看、谁能操作           | 用户确认过的规则                       |
| 协作权限位、项目状态名     | 枚举源码                               |
| 错误码                     | 错误码定义                             |
| 沿用的旧限制（状态、套餐） | 用户说「沿用现有规则」时，对照现有判断 |

完成：每条将写入的规则都有确认来源；需要核对的名字已经和源码对上。

## 3. 定章节

```
范围
└─ 总是写在最前。一两句，点出功能点名称

功能点
├─ 每个功能点一个二级标题
├─ 以页面上的实际组件为行，一张表
└─ 没有确认过的功能点 → 整节省略
```

表列是「组件」「效果」「出现条件」「操作条件」「操作失败提示」「说明」。组件用页面上的名称。效果写该组件做成什么事，一句，不写权限。

- 出现条件：决定出不出现
- 操作条件：决定能不能点。置灰用的状态、套餐写在这里
- 操作失败提示：点下去之后的失败文案，不写错误码编号
- 说明：补充。不重复前三列

同一格里一条约束一行，行与行之间用 `<br>`。不写「同上一行」这类对照。表的写法见 [templates.md](templates.md)。

完成：范围已列入；每个确认过的功能点有一节和至少一张表；未确认的功能点没有节。

## 4. 写入

把定下的节写入目标路径，放在 frontmatter 之后。

- 第一个二级标题是 `## 范围`
- 功能点的规则放在表格里，节内不再用列表复述同一批场景
- 状态用枚举里的中文名
- 用户明确说沿用现有限制时，把该限制写进它造成置灰或失败的那一列
- 不写函数名、文件路径和调用顺序

完成：文件已写入；章节与第 3 步一致；正文与第 2 步的事实一致。

## 5. 自检

- [ ] frontmatter 的键和值与写入前一致
- [ ] 正文以 `## 范围` 开头，范围只有一两句
- [ ] 每个功能点是一个二级标题。行是页面上的实际组件，列是「组件、效果、出现条件、操作条件、操作失败提示、说明」。效果只写业务功能。同一格内一条约束一行
- [ ] 每条规则都能对上一次用户确认
- [ ] 权限位、错误码、状态名与源码一致
- [ ] 没有函数名、文件路径、curl 或 DDL
- [ ] 未确认的分支没有写进正文

完成：每一项为通过，或不适用并注明原因。
